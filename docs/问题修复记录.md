# 项目问题与修复记录

本文档记录「集物志 · 二手书管理系统」在**本地开发**与**云服务器部署**过程中实际遇到的 8 个问题。每个问题明确说明：

- **出错位置**：错误发生在哪一层、哪个文件、哪段配置
- **现象**：用户视角看到什么
- **排查过程**：如何一步步定位
- **根本原因**：为什么会错
- **解决方法**：具体怎么改（含命令）
- **验证结果**：怎么确认修好了

**部署架构**：Ubuntu 云服务器（腾讯云 CVM）→ nginx（对外 8080）→ Node.js/Express（3001，systemd 托管）→ MySQL（3306，仅内网）

## 问题 1：本地登录失败，疑似接口故障

**出错位置**：**运行环境层，不是代码**——① Windows 服务 `MySQL80` 处于停止状态；② 后端 3001 端口无进程（`server.js` 启动时会先测试数据库连接，连不上就主动退出，见其 `startServer()` 函数）。

**现象**：本地用测试账号（20260001 / 123456）登录失败，怀疑接口代码有问题。

**排查过程**：
1. 检查登录接口源码（`server.js` 的 `POST /api/v1/users/login`）：逻辑正常
2. 命令行检查运行环境：`sc query MySQL80` 显示 STOPPED；`netstat` 显示 3001 端口无监听
3. 前端日志 `vite-preview-error.log` 明确记录：`/api/v1/users/login → ECONNREFUSED`（连接被拒绝）

**根本原因**：数据库服务和后端都没有启动。登录请求经 Vite 代理转发到 3001，无进程接收 → 连接被拒绝。

**解决方法**：
```bat
:: 1. 先启动数据库（需管理员权限，可双击项目里的 启动MySQL服务.bat）
net start MySQL80
:: 2. 再启动前后端（或双击 启动项目.bat）
npm run dev:all
```

**验证结果**：服务启动后测试账号登录成功。

**经验**：报错要分层判断——「接口报错」和「服务没起来」在外层表现相似，先用端口监听状态和日志定位到具体层级。

## 问题 2：线上租借管理页"暂时无法加载/获取失败"

**出错位置**：**线上数据库**——`rent_requests` 表缺少 `deleted_by_owner`、`deleted_by_requester`、`returned_at` 等字段（用到这些字段的 SQL 在 `config/platform-routes.js`）。**错因在部署流程**：首次部署只执行了建表脚本 `config/init-db.js`，**没有执行 11 个 `config/migrate-*.js` 迁移脚本**。

**现象**：线上「交易订单」页显示"暂时无法加载"，接口返回 `500 {"error":"Unknown column 'r.deleted_by_owner' in 'where clause'"}`。

**排查过程**：
1. 本地一切正常，只有线上报错
2. 从接口报错定位到 SQL 引用的字段
3. 用脚本导出**本地与线上的全部表+列**逐一对比，确认线上缺列

**根本原因**：`init-db.js` 只创建**基础表结构**；后续功能演进产生的 11 个迁移脚本（给已有表追加字段）从未在全新线上库执行过。本地数据库是长期演进而来的（每个迁移都跑过），所以本地正常。

**解决方法**：在服务器项目目录依次执行全部**幂等**迁移脚本：
```bash
cd /home/ubuntu/library-mgmt
for m in add-security platform idcard buyout orders rent-return \
         rentals-seen rentals-precision social trade-history user-role; do
  node config/migrate-$m.js
done
```
⚠️ 唯一**不能**对全新库执行的是 `config/migrate-db.js`（旧库改造脚本，含 `DROP COLUMN`，全新库不适用）。

**预防措施**：
- 部署前先做「结构对比」：导出本地与线上表结构 diff，一次性找全差异
- 统一使用幂等同步脚本 `scripts/bootstrap-db.js`（`CREATE TABLE IF NOT EXISTS` / 先查再加字段，只补不删、可重复执行）

**验证结果**：接口恢复 200，全站接口体检通过。

## 问题 3：部署后网站返回 500（Permission denied）

**出错位置**：**服务器文件权限**——目录 `/home/ubuntu` 权限为 `750`，nginx 工作进程（www-data 用户）无法"穿过"该目录读取前端文件。报错记录在 `/var/log/nginx/error.log`。

**现象**：部署完成、所有服务已启动，但访问网站首页返回 500。

**排查过程**：nginx 错误日志显示：
```
stat() "/home/ubuntu/library-mgmt/dist/index.html" failed (13: Permission denied)
```

**根本原因**：Ubuntu 默认把用户主目录设为 `750`（仅属主可进入），而网站文件放在 `/home/ubuntu/library-mgmt/dist` 下，nginx 无权访问。

**解决方法**：
```bash
sudo chmod o+x /home/ubuntu   # 允许"穿过"目录（内容仍不可列出，兼顾安全）
```

**验证结果**：首页恢复 200。

## 问题 4：部署脚本执行到数据库初始化后挂起

**出错位置**：**代码缺陷**——`config/init-db.js` 直接运行时，**成功分支没有调用 `process.exit()`**；而模块使用的数据库**连接池**保持活动状态，Node 进程执行完任务后不退出。

**现象**：一键部署脚本执行到 `node config/init-db.js` 后卡住不返回，后续步骤（systemd 配置、nginx）未执行。

**排查过程**：SSH 连上服务器查看进程列表，发现 `node config/init-db.js` 进程仍在运行（任务已完成但没退出）。

**解决方法**：
1. 清除挂起的进程，手动补完剩余部署步骤
2. 后续部署流程**不再执行 `init-db.js`**（它含 `DROP TABLE`，重跑会**清空数据**），改用 `scripts/bootstrap-db.js`——幂等、只补不删、执行完主动关闭连接池并正常退出

**验证结果**：改用 `bootstrap-db.js` 后部署脚本每次都能正常执行到底。

## 问题 5：新功能上线后点赞接口 500

**出错位置**：**线上数据库**缺少 `post_likes` 表；**错因是脚本维护不同步**——新增的 `post_likes` 表只写进了 `config/init-db.js`（仅全新安装时生效），没有同步到迁移脚本和 `scripts/bootstrap-db.js`。

**现象**：帖子点赞功能部署后，点赞接口报错（数据表不存在）。

**排查过程**：对比新旧 `init-db.js` 发现新表只加在"全新安装"路径；已有的线上库既不会执行 `init-db.js`，也没有对应的迁移脚本。

**解决方法**：
1. 在线上库执行建表 SQL（与 `init-db.js` 中定义一致）
2. 将该表 DDL 同步加进 `scripts/bootstrap-db.js`
3. 确立规则：**`init-db.js` 与 `bootstrap-db.js` 必须同步维护**——前者管全新安装，后者管已有库升级

**验证结果**：发帖 → 点赞 → 取消赞 → 删帖全链路 E2E 通过。

## 问题 6：本地反复提示"服务暂时不可用"

**出错位置**：**本地运行环境**——同一台电脑上同时存在两套开发环境：5173 端口（旧实例，进程已退出但浏览器还停留其页面）与 5174 端口（新实例）。浏览器停在 5173 的标签页上，所有请求发不到任何后端。

**现象**：本地页面操作时提示"服务暂时不可用，请确认后端已启动后重试"。

**排查过程**：
1. 逐段测试链路：本地后端直连（3001）✅、经 Vite 5173 代理 ❌（连不上）、经 5174 代理 ✅、线上 ✅
2. 用 `Get-CimInstance` 查看进程发现 5173 的进程已不存在（死实例），5174 才是活着的

**根本原因**：反复运行启动脚本产生了多套实例；旧实例退出后，停留在旧标签页的请求全部失败。

**解决方法**：
1. 清理全部残留进程
2. 统一操作规范：**启动前先关闭所有旧窗口和旧标签页，启动脚本只运行一次**（重复运行会导致端口冲突，第二个实例报"启动失败"属正常现象）

**经验**：「服务暂时不可用，请确认后端已启动后重试」是前端**连不上后端时的通用提示**，不代表后端一定没启动——要按链路逐段排查（浏览器 → nginx/Vite → 后端 → 数据库）。

## 问题 7（最典型案例）：线上头像/封面上传全部失败（404）

**出错位置**：**服务器 nginx 配置**——文件 `/etc/nginx/sites-available/library` 中的写法：
```nginx
location /uploads/ {          # ← 错在这里：带了尾斜杠
    proxy_pass http://127.0.0.1:3001;
    proxy_set_header Host $host;
}
```

**现象**：线上「个人中心」更换头像时，浏览器控制台报 `GET /uploads/ 404`，头像无法保存（数据库 `avatar_url` 始终为 NULL），反复尝试多次均失败。

**排查过程**：
1. 查数据库：确认头像字段为空，说明保存请求从未成功
2. 查 nginx 访问日志，得到决定性证据：
```
POST /uploads        → 301（被 nginx 重定向）
GET  /uploads/       → 404（浏览器自动跟随 301，且把 POST 变成了 GET）
```

**根本原因**：nginx 对结尾带斜杠的 `location`（如 `location /uploads/`）有一个特殊行为：**对不带斜杠的同名请求（`/uploads`）自动返回 301 跳转到 `/uploads/`**。而浏览器跟随 301 重定向时，会把 **POST 请求转换为 GET**——于是"上传图片"变成了"读取一个不存在的目录"，返回 404，上传永远无法成功。

**影响范围**：前端**头像、商品封面**的上传接口是 `POST /uploads`（不带尾斜杠）→ 全部失败；**聊天附件**走 `/uploads/chat`（多了一段路径）→ 不受影响，因此问题隐藏较深。

**解决方法**：把 nginx 配置中的 `location /uploads/` 改为 `location /uploads`（**去掉尾斜杠**）：
```nginx
location /uploads {           # ← 去掉尾斜杠后，/uploads 与 /uploads/xxx 都能正确匹配
    proxy_pass http://127.0.0.1:3001;
    proxy_set_header Host $host;
}
```
```bash
sudo nginx -t                  # 测试配置
sudo systemctl reload nginx    # 重载生效
```

**验证结果**：
```
POST /uploads → 200 {"url":"/uploads/xxx.png"}   上传成功
GET  /uploads/xxx.png → 200 image/png             文件可正常访问
```

**经验**：nginx 里凡是**客户端可能不带斜杠访问**的前缀路径（如 `/uploads`、`/api`），`location` 都不要带尾斜杠，否则会触发 301 并把 POST 请求"降级"为 GET。

## 问题 8：部署到云服务器后，页面一直提示“后端没开”

**用户提问**：我已经部署到云服务器上了，但是出错一直显示“服务暂时不可用，请确认后端已启动后重试”，怎么办？

**出错位置**：目前已定位到**线上请求链路**——浏览器请求 `/api/...` 后拿到的内容不是后端应返回的 JSON。具体断点可能位于 API 进程、nginx/Caddy 反向代理，或实际部署入口；需要结合服务器状态与日志作最后确认。

**现象**：云服务器上的网页能够打开，但在个人资料等页面保存数据时显示：
```
服务暂时不可用，请确认后端已启动后重试
```

**代码判断依据**：该提示来自 `src/api.js`。前端收到响应后会先读取正文，再执行 `JSON.parse(text)`；只有响应正文无法解析为 JSON 时，才会抛出这句提示：
```js
const text = await response.text()
let data = {}
try { data = text ? JSON.parse(text) : {} }
catch { throw new Error('服务暂时不可用，请确认后端已启动后重试') }
```
因此，该提示**不能直接证明后端没有启动**。它更准确的含义是：前端预期收到 JSON，却收到了 HTML 或其他非 JSON 内容。常见情况包括 nginx 的 502 页面、静态站点的 `index.html`，或云平台自己的错误页面。

**排查过程与执行顺序**：按照本文档开头记录的实际部署架构，从后端到公网入口逐段测试：
```bash
# 1. 确认 3001 端口是否有后端进程监听
sudo ss -lntp | grep ':3001'

# 2. 绕过 nginx，直接访问 Express 后端
curl -i http://127.0.0.1:3001/api/health

# 3. 再经过对外 8080 端口访问，验证 nginx 代理
curl -i http://127.0.0.1:8080/api/health

# 4. 检查 nginx 配置和错误日志
sudo nginx -t
sudo tail -n 100 /var/log/nginx/error.log

# 5. 找出后端 systemd 服务名并查看日志
systemctl list-units --type=service | grep -Ei 'library|node|jiwuzhi'
sudo journalctl -u <上一步查到的服务名> -n 200 --no-pager
```

健康检查正常时，正文应为：
```json
{"status":"ok"}
```

**按返回结果处理**：

1. 3001 没有监听，或直连 `127.0.0.1:3001` 失败：后端没有正常启动。查看 systemd 日志中的数据库错误，重点核对后端读取的 `.env` 中 `DB_USER`、`DB_PASSWORD`、`DB_NAME` 是否正确。
2. 3001 直连返回正常 JSON，但 8080 返回 HTML 或前端首页源码：请求落到了静态站点，说明 nginx 的 `/api/` 反向代理没有正确匹配。
3. 3001 直连正常，但 8080 返回 `502 Bad Gateway`：nginx 已匹配代理规则，但连接不到配置中的后端地址；检查 `proxy_pass` 是否为 `http://127.0.0.1:3001`，以及后端监听状态。
4. 3001 和 8080 均返回 `{"status":"ok"}`：服务器内部链路正常，应继续检查公网域名、云平台/宝塔的二级反向代理，以及实际访问请求是否进入当前 nginx 实例。

**如果服务器已经改为 Docker Compose 部署**：不要使用上面的 systemd 状态判断，改为检查四层容器并启动完整服务，不能只上传前端 `dist`：
```bash
docker compose --env-file .env.production ps
docker compose --env-file .env.production logs --tail=200 db-init api web gateway
docker compose --env-file .env.production up -d --build
```
服务器安全组开放 TCP 80、443 即可；3001 和 3306 不应直接暴露到公网。

**处理结论**：依据前端代码将问题从模糊的“后端没开”缩小到“`/api` 返回非 JSON”，再按 3001 后端直连、8080 nginx 入口、公网入口的顺序分层排查处理。用户已确认线上故障解决。具体命中的故障点和实际执行的修复命令尚未反馈，因此本文不虚构根因；后续取得服务器操作记录后可继续补全。

**后续验证标准**：

- 公网访问 `https://实际域名/api/health` 返回 HTTP 200 和 `{"status":"ok"}`
- 浏览器网络面板中的业务接口返回 JSON，而不是 HTML/502 页面
- 重新保存个人资料成功，页面不再出现“请确认后端已启动”的提示

**验证结果**：用户已于 2026-10-10 确认问题解决。✅

## 经验总结

1. **分清故障层级**：环境（服务/端口）→ 代理（nginx/Vite）→ 应用（接口）→ 数据库，逐层排查，不要被外层症状误导（问题 1、6）
2. **全新数据库 = 建表脚本 + 全部迁移脚本**：缺一不可；维护两个入口（`init-db.js` 管全新安装、`bootstrap-db.js` 管已有库升级），并保持同步（问题 2、5）
3. **迁移脚本坚持幂等**：可重复执行、只增不删，才能在任意状态的库上安全运行（问题 2）
4. **部署前做结构对比**：本地与线上导出表结构 diff，把差异消灭在部署前（问题 2 的预防措施）
5. **nginx 路径匹配的细节陷阱**：`location` 尾斜杠 + `proxy_pass` 会产生 301，对 POST 请求是致命的（问题 7）
6. **看日志下结论**：nginx access/error 日志、`journalctl -u <服务>`、浏览器控制台，三个来源组合起来才能定位真实原因（问题 2、3、7）
7. **前端提示不等于根因**：“请确认后端已启动”只是 JSON 解析失败后的通用提示；应通过 `/api/health`、容器状态和代理日志判断收到的是静态首页、502 页面还是正常 JSON（问题 8）
